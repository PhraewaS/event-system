## 1. ปัญหาที่ต้องการปรับและเหตุผล

เดิม Participant สามารถลงทะเบียนหลายกิจกรรมในวันจัดกิจกรรมเดียวกันได้ไม่จำกัดจำนวนรวม หากแต่ละคำขอผ่าน duplicate/deadline/capacity rules การเปลี่ยนครั้งนี้กำหนดโควต้ารายบุคคลเพื่อจำกัดการจองหลายกิจกรรมในวันเดียวกันและแจ้งเหตุผลปฏิเสธให้เข้าใจได้

เป็น requirement ใหม่ของทีม ไม่ได้อ้างว่าพฤติกรรมเดิมผิดสัญญา หรือเป็นการแก้บั๊ก Location/Description ของ #76 ซึ่งแก้เสร็จแล้ว

## 2. กฎเดิม → กฎใหม่

| หัวข้อ | ก่อนเปลี่ยนที่ accepted baseline | กฎใหม่ที่เสนอให้ teammate ยืนยัน |
| --- | --- | --- |
| จำนวนรวมต่อวัน | ไม่จำกัดจำนวนกิจกรรมต่าง event IDs | ไม่เกิน **2 registrations ต่อ Participant ต่อวันเริ่มกิจกรรม**; schema Sprint 1 ปัจจุบันนับทุกรายการ ส่วนการไม่นับ CANCELLED เป็น dependency เมื่อเพิ่ม Sprint 2 ตาม §3 |
| นิยามวัน | ยังไม่มีกฎโควต้า | วันที่จาก `events.starts_at` ใน **Asia/Bangkok** ไม่ใช่วันที่กดจอง วันของ deadline หรือ timezone ของ browser |
| คำขอเพิ่มเมื่อเต็ม | ผ่านได้ถ้ากฎรายกิจกรรมผ่าน | `409 DAILY_REGISTRATION_LIMIT`, ไม่ insert, ไม่ลดที่นั่ง, session ยังใช้งานได้ |
| ความเป็นอิสระ | จำกัดคนเดิมซ้ำ event เดิมและ capacity ราย event | เก็บกฎเดิม และแยก quota ตาม user/date; คนละวันหรือคนละคนมี quota แยก |
| คำขอพร้อมกัน | ล็อก event เพื่อป้องกัน capacity เกิน | ต้อง serialize การแก้ registration ของ Participant เดียวกันข้าม event ด้วย; user → event lock order |
| ข้อมูลเดิม | แสดงรายการที่เคยลงทะเบียน | เก็บทุกรายการ แม้เดิมมีมากกว่า 2 ในวันเดียวกัน; existing count ≥ 2 ปฏิเสธรายการเพิ่ม |
| การแสดงผล | แสดงสถานะกิจกรรม/รายการตน | Participant เห็น quota ของตัวเองตามวันไทยบน event detail และเข้าใจ error; public data ไม่เพิ่มข้อมูลส่วนบุคคล |

การผ่านไปของเวลาเริ่มกิจกรรมไม่คืน quota ของวันนั้นโดยอัตโนมัติ การนับผูกกับวันเริ่มกิจกรรมและสถานะ registration ตามกฎที่มีอยู่ ไม่เพิ่มการตรวจเวลาซ้อนทับหรือจำนวนชั่วโมงของกิจกรรม

## 3. ขอบเขต

รวม: registration transaction, private quota query, field/API definitions, UI ของ Participant, privacy, timezone boundaries, concurrency, legacy records และ regression ของ F-01–F-04

ไม่รวม: waitlist, quota ที่ปรับราย Organizer/ราย event, ระบบแจ้งเตือน, เปลี่ยนวัน/เวลางานที่เผยแพร่แล้ว, payment, การทำ cancellation/capacity/check-in แทน Sprint 2/3 หรือการเปลี่ยนโครงสร้าง auth/session

Sprint 2 #8 ยังต้องมี contract และ implementation ของตน เมื่อเพิ่ม CANCELLED/reactivation ภายหลังต้องนับเฉพาะ ACTIVE และตรวจ quota ตอน reactivation ด้วย ส่วนนี้เป็น dependency ของสัญญา ไม่อ้างว่ามี cancellation แล้วใน Lab 7

## 4. เงื่อนไขสำคัญที่ต้องยืนยันก่อน code

- คงลำดับ rejection เดิม: duplicate → closed deadline → event full แล้วจึง daily quota
- คืน quota ของตนผ่าน GET เท่านั้น ไม่รับ participant ID เพื่อเลือกผู้อื่น; role/ownership และ CSRF เดิมคงอยู่
- เลือกวันด้วย Thai calendar boundaries รวมเที่ยงคืนและกรณี UTC คนละวันแต่ไทยวันเดียวกัน
- ข้อมูลเกินโควต้าก่อนเปลี่ยนยังดูได้และไม่ถูกลบ ลด หรือย้ายวัน
- บันทึก rejected request พร้อมตรวจว่า event count/roster และ registration IDs ไม่เปลี่ยน
- เตรียม tests แบบแข่งคนเดียวกันต่าง event และต่างคนแย่งที่นั่งสุดท้าย เพื่อรักษา invariant ทั้ง quota และ capacity

รายละเอียดที่ใช้ implement และตัดสินผลคือ [daily-quota-contract.md](daily-quota-contract.md) ไม่ใช้บทสรุปนี้แทน AC/STS
